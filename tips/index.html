写作提示与常见错误 · Tips

一、先用 Vars + watch 字段把逻辑调通

Vars 是 CD2 里最强大、也最容易被新作者忽略的模块。它远不只是个调试工具，至少能同时帮你做三件事：

  • 判断自己的代码有没有问题：把想验证的表达式接进一个变量，打开 Watch，它的值就会直接显示在游戏 UI 上。关键在于：一旦代码写出问题，这个变量就会什么都不显示——所以「屏幕上找不到它」本身就是一个明确的报错信号。对刚上手写难度的作者来说，这一点的价值怎么强调都不过分。
  • 储存信息，让代码更简洁：变量定义一次之后，就能在任何接受同类型值的地方用 {"Var": "变量名"} 引用。把重复出现的表达式抽成一个变量，代码会短很多，日后要改也只需要改一处。
  • 让模块之间能够通信：所有变量在同一时刻统一更新，因此它在各个模块里读到的值始终一致。

一个必须知道的限制：变量之间不能形成循环依赖。

  • 允许 —— 链式引用：A → B → C。C 的 Value 里用 {"Var": "B"}，B 里再用 {"Var": "A"}，一路单向往下走多少层都行。
  • 报错 —— 循环引用：A → B → A。B 引用了 A，而 A 又回头引用 B，绕成一个圈。

即使你用手动制造延迟的办法把两者在时间上错开，循环仍然会直接报错——变量是用来「汇总」的，不是用来互相串的。

写 Mutator 最难受的是「不知道到底有没有生效」。推荐做法：在 Vars 里定义一个变量，把想验证的表达式接进去，然后在游戏里用 watch 实时看它。

json
"Vars": {
    "调试-击杀超过10": {
        "Type": "Boolean",
        "Watch": true,
        "Value": {
            "Mutate": "IfFloat",
            "Value": {"Mutate": "EnemiesKilled"},
            ">": 10,
            "Then": true,
            "Else": false
        }
    }
}

布尔变量最适合当 watch：你一眼就能看出条件在哪个时刻变成 true。比起反复改难度、进游戏试，这条路快得多。

二、CD2 的下标从 0 开始

这是很容易踩的一个坑：CD2 里凡是「按序号取第几个」的字段，序号都从 0 开始数。

  • SelectFromArray：Select 返回 0 → 取数组第 1 个；返回 1 → 取第 2 个，以此类推。
  • Sequence：同理，0 对应序列的第一项。

写映射表时不要按「第几个」去数，要按「从 0 开始的序号」去数——差一位是最常见的调试来源。

三、Mutator 不是瞬时响应的

Mutator 采用轮询机制，信号变化到被识别之间约有 0.5 秒延迟。用击杀数、血量这类高频变化的量做精确计时时，要把这段延迟算进去。

四、随机类 Mutator 的返回值是持续变化的

Random、RandomChoice 等随机类 Mutator，只要被求值就会返回一个结果——在设定范围内每一次取值都可能不同。也就是说，它们不是「摇一次就固定下来」，而是随着求值不断变化。

如果希望一个随机结果固定下来，有两种做法：

  • 使用 RandomChoicePerMission：它只在任务开始时抽取一次，之后保持不变。
  • 用 LockFloat / LockBoolean / LockString 等锁定类 Mutator 把随机结果锁住。如果还想把这个值存下来反复引用，可以把它放进 Vars，这样也能和其它 Vars 配合，做出更复杂的效果。

五、「一瞬间」的布尔信号能干什么

很多触发器（例如 TriggerOnChange）产生的 True 只持续一瞬间，但它并不等于没用：

  • 大部分布尔字段会被一瞬间的信号正常激活一次；
  • 波次生成器这类带 Interval 的字段要留意：Interval 比信号持续时间长时，它可能一直在等下一次，结果根本不生成；Interval 设得短，一瞬间的信号也能触发一次生成。

结论：能不能用取决于目标字段，建议实际跑一次再下结论。确实需要一段稳定的持续窗口时，用 TriggerFixedDuration 把信号拉长。

六、生成数量与点数：两个容易踩的坑

实际会多刷一只 · MaxSpawnCount

波次的实际点数充足时，MaxSpawnCount 限制的数量会多生成 1 只——写成 3 时可能看到 4 只。做数量控制时要按这个来预留余量。

用「母体 + 自定义变种」控制生成，而不是直接调敌人本身

如果想控制某种敌人刷出多少、多稀有，直接在该敌人身上设置数量、稀有度或点数并不可靠——它仍然可能被波次刷出来。

更稳的做法是：放一个母体单位，用它的自定义变种（CustomVeterans）字段去改成你想要的目标敌人。这样数量与稀有度的控制就落在母体上，目标敌人本身不再受波次直刷的影响。

另外，WaveSpawner 的波次实际点数，推测约为 Difficulty × EnemyCountModifier（此式未在官方文档中确认，仅供参考）。

七、常见错误写法

❌ 是错误写法，✅ 是修正写法。

① 把数值型 Mutator 直接喂给需要布尔信号的字段

In、If 的 Condition 等字段要求布尔信号，而 DwarvesDown、EnemiesKilled 这类 Mutator 返回的是数值。数值输出必须先经 TriggerOnChange 转换。

json
❌ "In": {"Mutate": "DwarvesDown"}

✅ 用 TriggerOnChange 读取；只想在数值上升时触发就加 RiseOnly：

json
"In": {
    "Mutate": "TriggerOnChange",
    "RiseOnly": true,
    "In": {"Mutate": "DwarvesDowns"}
}
