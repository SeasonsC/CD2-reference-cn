写作提示与常见错误 · Tips

这一页是我们自己踩过的坑，以及给新作者的建议，不属于官方文档的翻译内容。

一、先用 Vars + watch 字段把逻辑调通

Vars 是 CD2 里最强大、也最容易被新作者忽略的模块。它远不只是个调试工具，至少能同时帮你做三件事：

  • 判断自己的代码有没有问题：把想验证的表达式接进一个变量，打开 Watch，它的值就会直接显示在游戏 UI 上——逻辑写错、类型对不上、条件根本不成立，这些几乎都能一眼看出来。对刚上手写难度的作者来说，这一点的价值怎么强调都不过分。
  • 储存信息，让代码更简洁：变量定义一次之后，就能在任何接受同类型值的地方用 {"Var": "变量名"} 引用。把重复出现的表达式抽成一个变量，代码会短很多，日后要改也只需要改一处。
  • 让模块之间能够通信：所有变量在同一时刻统一更新，因此它在各个模块里读到的值始终一致。

写 Mutator 最难受的是「不知道到底有没有生效」。推荐做法：在 Vars 里定义一个变量，把想验证的表达式接进去，然后在游戏里用 watch 实时看它。

"Vars": {
    "调试-击杀超过10": {
        "Type": "Boolean",
        "Watch": true,
        "Value": {
            "Mutate": "IfFloat",
            "Value": {"Mutate": "EnemiesKilled"},
            ">": 10,
            "Then": true,
            "Else": false
        }
    }
}

布尔变量最适合当 watch：你一眼就能看出条件在哪个时刻变成 true。比起反复改难度、进游戏试，这条路快得多。

二、Mutator 不是瞬时响应的

Mutator 采用轮询机制，信号变化到被识别之间约有 0.5 秒延迟。用击杀数、血量这类高频变化的量做精确计时时，要把这段延迟算进去。

三、「一瞬间」的布尔信号能干什么

很多触发器（例如 TriggerOnChange）产生的 True 只持续一瞬间，但它并不等于没用：

  • 大部分布尔字段会被一瞬间的信号正常激活一次；
  • 波次生成器这类带 Interval 的字段要留意：Interval 比信号持续时间长时，它可能一直在等下一次，结果根本不生成；Interval 设得短，一瞬间的信号也能触发一次生成。

结论：能不能用取决于目标字段，建议实际跑一次再下结论。确实需要一段稳定的持续窗口时，用 TriggerFixedDuration 把信号拉长。

四、常见错误写法

❌ 是错误写法，✅ 是修正写法。

① 把数值型 Mutator 直接喂给需要布尔信号的字段

In、If 的 Condition 等字段要求布尔信号，而 DwarvesDown、EnemiesKilled 这类 Mutator 返回的是数值。数值输出必须先经 TriggerOnChange 转换。

❌ "In": {"Mutate": "DwarvesDown"}

✅ 用 TriggerOnChange 读取；只想在数值上升时触发就加 RiseOnly：

"In": {
    "Mutate": "TriggerOnChange",
    "RiseOnly": true,
    "In": {"Mutate": "DwarvesDowns"}
}

② 拿「一直是 true」的长信号做「延长」

DuringExtraction、SecondaryFinished 这类信号一旦变 true 就会长时间保持 true（SecondaryFinished 会一直保持到任务结束）。对它们用 TriggerSustain 再延长 N 秒几乎没有意义——这类触发器是给短信号准备的。

❌ "Enabled": {
    "Mutate": "TriggerSustain",
    "N": 15,
    "In": {"Mutate": "DuringExtraction"}
}

✅ 先拿到一个短信号，再延长：

"Enabled": {
    "Mutate": "TriggerSustain",
    "N": 15,
    "In": {
        "Mutate": "TriggerOnChange",
        "RiseOnly": true,
        "In": {"Mutate": "DwarvesDowns"}
    }
}

反过来想把长信号缩短，要用 TriggerFixedDuration，而不是 TriggerSustain。
